## Confirmed code findings before the fixes

1. **Identical snapshot work repeats.** `MediaViewModel.refreshMetadata` calls `applyLibraryMetadata`, which skips equal metadata, but subsequently calls `scheduleLibraryDerivation` regardless. That schedules `LibraryDerivationActor.deriveSnapshot`, including all iOS group construction. Cancelling the previous task does not interrupt the synchronous actor calculation; the generation check protects publication only. A synthetic 20-request regression reproduced 20 rebuilds before BF-088.
2. **A successful Storyteller listing is committed to the cache twice.** `StorytellerActor.fetchLibraryInformation` calls `LocalMediaActor.updateSourceCacheMetadata`. Both shared `BookServiceActor.fetchLibraryInformation` entry points then call it again after adding the source display name. Each call rewrites cached metadata, reconciles server positions and notifies observers. When the server's `source` field is nil, the two writes may also alternate unnamed/named metadata. This duplication is confirmed in source; how many intermediate versions reached the iPad derivation actor is not observable in the supplied report.
3. **The periodic library loop ignores activity state.** `MediaViewModel` starts it; `BookServiceActor.startPeriodicLibraryRefresh` waits the smaller metadata/progress interval, then fetches all sources if any is connected. Defaults are 300 s metadata and 30 s progress. iOS background handling already calls `BookServiceActor.setActive(false, source: .app)`, but that only forwards activity to Storyteller's connection monitoring. It neither stops nor gates the library loop. This explains how library work can continue while the process remains runnable, but does not establish why this device stayed runnable for an hour.
4. **Failure counts do not identify a sync defect.** The foreground Storyteller position path returns success only for HTTP 204; other HTTP responses become failure, and transport errors become noConnection. `BookServiceActor` records both non-success results as failure. Existing debug messages record HTTP status/transport error. A server rejection of an older position can be a normal conflict; 401, 404, 409 and other errors require different actions. No status log accompanies this export. No change to acknowledgement, retry or conflict policy is justified by the 14 failures alone.

## Implemented increment: BF-088

The existing derivation actor retains its most recent input/result and reuses it for identical content. The publication generation is excluded from content equality and updated on each returned result. Synthesized equality includes every input field; locale and calendar are checked separately because sorting and shelf date predicates depend on them. Memory is bounded to one result/input, with no new persistence or dependency.

Every `library.index` request still records duration and outcome. Existing `cacheHits` and `cacheMisses` scalars now distinguish cheap reuse from complete derivation. This is the narrow measurement needed to evaluate the optimization; no new report schema or general instrumentation project is introduced.

This does not eliminate duplicate source-cache writes, genuinely changed intermediate snapshots, all cancelled work or the background polling loop. A hit still compares the complete input. No energy saving or on-device speedup is claimed from the synthetic regression.

## Follow-up changes authorized by the owner

1. **Implemented in BF-089: consolidate listing publication at one owner.** Preserve the source display-name fallback and unreadable-entry retention, then remove the duplicate cache update in the shared service. Keep backend-specific listing details inside the adapter and express any shared publication requirement through the source contract. Test a complete listing, nil source labels, unchanged repeated listings, unreadable entries, removed/relisted downloaded books, pending progress/metadata edits and write failures. Do not merely delete the second call: it currently supplies normalized labels, and persistence failures are swallowed in both paths.
2. **Implemented in BF-090: make periodic full-library refresh activity-aware.** Use the shared service's existing activity entry point, track all relevant active surfaces, and pause the optional full-library poll when none needs it. Preserve final/background outgoing reading-position delivery and automatic backup owners. Establish the desired incoming-position behavior during background audio/CarPlay, then test foreground return, settings changes while paused, account changes and a poll already in flight. The code supports this recommendation now; the export alone does not choose those interaction details.
3. **Classify the observed reading-position failures using existing logs.** Match a synthetic reproduction's `sendProgressToServer: status=…` or transport error with queue history. Only add a finite failure-category counter if those existing diagnostics cannot capture the event. Do not infer lost progress or change conflict handling from the aggregate failure ratio.
