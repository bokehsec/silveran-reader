# ADR 006: Exact legacy capture and restartable annotation staging

- Date: 2026-09-30
- Status: Accepted for capture/staging; reader cutover remains gated
- Scope: Kit legacy migration planner, repository recovery originals and schema 3
- References: [plan P2.4](../ANNOTATION_SYNC_BACKUP_IMPLEMENTATION_PLAN.md), [repository ADR](003-transactional-annotation-repository.md), [identity ADR](004-edition-anchors-and-creative-conflicts.md), [restore ADR](005-annotation-snapshots-and-transactional-restore.md)

## Decision and lifecycle

Storage owners supply an immutable schema-1 inventory capture containing exact original bytes, an opaque file identity, format, explicit source/account/book ownership where verified, and distinct missing/unreadable states. File identities are labels, never extraction paths or evidence of book ownership. No title, filename, unscoped server UUID or matching passage supplies an owner. The capture itself does not prove that every file was enumerated or that several owners observed one generation.

A dedicated empty staging repository commits the complete capture and its SHA-256 fingerprint before importing any creative records. A second transaction validates the journal, builds a plan, imports known typed records plus separate backup intent, verifies the entire staged snapshot against the plan, and commits its verification. Both transactions are nonsuspending within one repository actor and use the existing SQLite transaction boundary. Failure during import retains the earlier durable raw capture and rolls back every staged record, head, intent and verification update. Restart resumes by the same capture UUID. Reusing a capture identity with different originals or ownership, multiple capture rows, unknown journal data, a damaged checksum, occupied repositories or independently added staging work is refused.

Keep original bytes indefinitely, including supported records whose decoding fills documented legacy defaults. Known schema-1/2 ink preserves IDs, strokes, dates, quote selectors and legacy CFIs. V2 bookmarks/highlights/typed notes preserve their complete payload and locator. Migration does not synthesize edition identity or a normalized selector for typed highlights. Future, corrupt, mixed/unknown-field or unidentified files remain recovery originals rather than partially imported collections. Unreadable originals remain an explicit unavailable entry; their absent bytes cannot be reported as backed up. Released source-unscoped highlight files remain recovery material until ownership can be established deliberately; this new importer does not repeat the old multi-owner mapping heuristic.

## Operation identity and conflicts

Migration operation IDs use a documented SHA-256-derived UUIDv8: hash canonical JSON containing the fixed domain `silveran/legacy-annotation-migration/v1`, explicit scope and complete typed document; take the first 128 bits; set version 8 and RFC variant bits. [RFC 9562 sections 5.5/5.8](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.8) requires SHA-256 name-based UUID designs to use version 8 rather than version 5 and leaves their uniqueness to the implementation. The maintained existing Swift Crypto fingerprint supplies the hash; no new dependency or custom cryptography is introduced. UUID truncation is not authentication, and any identity/content collision must be refused by the existing immutable-command contract.

Repeated capture on another device, inventory ordering, raw JSON formatting or an inventory-label change cannot assign another operation to the same scoped typed document. A changed creative payload produces another root revision rather than overwriting a previously imported root; later reconciliation must preserve or explicitly resolve both. The synthetic origin `legacy-migration-v1` records migration provenance, not a claim about the authoring device. Existing annotation IDs remain unchanged. Colliding annotation IDs within one scoped capture fail staging; selecting a winning type or regenerating IDs would hide creative data. Captures with such collisions remain durable for recovery.

The alternative of random import UUIDs would require an additional persisted per-record mapping before every retry and could duplicate annotations if that mapping were lost. Timestamp-based IDs or whole-book replacement would conflate independent creative work. A permanent JSON side journal would introduce another durability owner; storing capture and verification with the selected repository retains one transaction engine and a portable recovery participant.

## Schema, backup and rollback

Schema 3 adds `legacy_capture(capture_id, capture_hash, capture, verification)`. Fresh databases create all tables and marker in one transaction. Schema 1 upgrades create restore-checkpoint and capture tables; schema 2 upgrades add only capture. Failure or process loss leaves the previous marker/table generation consistent. Previous repository builds refuse unknown schema 3. The reader still uses protected legacy actors, so this increment does not activate migration, alter user originals or switch authority.

Expose retained capture IDs/originals for the future full archive participant. Annotation logical snapshots alone do not include these originals or certify full recovery. A verification's `allCapturedFilesDecoded` means every supplied entry decoded or was explicitly missing; an empty/incomplete supplied inventory is not proof of a complete library. Before cutover, storage owners must freeze/version and revalidate every required original, finish native payload portability, establish inventory completeness, verify counts/identities/editable payload hashes, and commit an application authority marker. After post-cutover edits exist, never reopen stale original JSON as the writer; use compatible recovery or a tested reverse migration.

## Validation and remaining acceptance

`LegacyAnnotationMigrationTests` covers exact original/payload equality, missing-book and account/source ownership, schema-1 CFI retention, corrupt/future/unknown/unassigned/unreadable categories, restart/idempotency, failure before capture/import commits, journal checksums/unknown nested fields, stable operation IDs, collisions, independent work refusal and atomic schema-2 upgrade with retained creative/checkpoint data. Existing schema-1 upgrade and future-database protection tests remain in the combined suite.

The macOS child harness compiles against the exact namespaced engine. It writes/spills a raw capture and exits before or after COMMIT, proving recovery distinguishes absent from durable capture. It spills deliberately unfinished storage rows and verification, exits without rollback/close, then proves reopening retains the raw capture, drops unfinished work and permits the real migration API to resume. Schema-1 and schema-2 migration markers are also interrupted before/after commit. This is selected SQLite-boundary process-loss evidence; it does not establish physical power-loss durability, the future owner-freeze/cutover boundary, native conversion fidelity, large-library/device memory budgets or non-Apple runtime acceptance.

No phase exit gate is passed by staging alone. Complete owner enumeration, cutover adapters/journal, undo/conflict-aware editing, full archive participants and all device/cloud/server gates remain open. Exact commands/results are recorded in the plan's progress entry.
