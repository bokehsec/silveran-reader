# ADR 013: Recoverable mutations for active annotation files

- Date: 2026-10-02
- Status: Accepted engineering direction for the authorized integrity remediation; implementation and acceptance tracked separately in the execution plan.
- Scope: Kit protected annotation owners, sync bookkeeping, recovery, identity moves and backup/restore coordination; Apple transport applies the receipt barrier.
- References: [inventory/protocol](../ANNOTATION_MUTATION_RECOVERY_PROTOCOL.md), [execution plan](../ANNOTATION_INTEGRITY_EXECUTION_PLAN.md), [ADR 003](003-transactional-annotation-repository.md), [ADR 009](009-backup-archive-and-icloud-transport.md), [ADR 010](010-live-icloud-annotation-sync.md), [ADR 011](011-active-typed-anchors-and-edition-evidence.md), [ADR 012](012-cross-device-library-identity.md).

## Decision and alternatives

Harden the active protected files with an explicit recoverable journal. Retain `InkActor` and the protected highlights owner as the only payload writers. The coordinator serializes domain commands and checks expected state; the journal owns durable intent/evidence, not a second annotation collection. SQLite repository cutover remains a separately measured/gated project (ADR 003/IP-6). Independent atomic payload/state writes are rejected because failure between files can lose conflict history or reinterpret remote work as a new local edit. Actor isolation alone is rejected because owner calls suspend and external readers/editors do not acquire the engine's locks.

Latest-clock annotation policy and stroke union-minus-erased semantics remain ADR 010. **Conservative retention revision:** automatic expiry of 180-day tombstones is suspended until long-offline rejoin/recovery acceptance demonstrates a safe policy. Existing tombstones remain; no cloud deletion is requested merely because of age. This deliberately supersedes ADR 010's automatic 180-day removal, trading metadata growth for prevention of undocumented resurrection while integrity is unverified. A bounded retention/rejoin design requires a later recorded decision and fixtures.

## Operation protocol

1. Validate raw envelopes/schema and source/account context. Distinguish missing, valid, corrupt, unreadable and unsupported state; protect original bytes and block unsafe writes. Unknown received creative fields remain raw in the inbox before any decoding/translation. Current reader validation (ADR 011/BF-043) still applies.
2. Persist original incoming operation and opaque transport fields under a stable digest of canonical envelope bytes. Duplicate delivery resolves to that same operation; failure means no durable receipt and no cursor advancement. Inbox retention is pending, not saved/applied completion.
3. Acquire affected books in stable `BookID` order; restore holds a barrier across books and affected sessions. Before accepting an external replacement, settle pending editor work or retain it durably and refuse/defer replacement. Validate expected owner state at commit, including absence and generation; observing earlier state is insufficient.
4. Compute the resolved operation once: raw before/after payloads, actual affected identity and href, expected/result hashes, full next sync entry/state, reserved clock, preserved cloud identity/scope and delivery intent. Persist that journal before applying through the owner. Losing creative versions/tombstones are durably retained with deterministic record identity before replacement; failed retention leaves the old committed payload intact.
5. Apply through protected owner compare-and-set. If current state equals expected, apply; if it already equals intended result, recognize replay. If neither matches, preserve both and block for reconciliation; never overwrite an unrelated edit or invent a fresh clock to hide incomplete application.
6. Persist resolved metadata/index/clock and completion. Publication and applied-success notification are eligible only after completion. Owner signals that fire earlier are held/deferred by the coordinator/transport gate. Never clear pending after network success if acknowledgement persistence fails.
7. Restart enumerates/validates unfinished intents before normal reconciliation/publication. Completed payload with incomplete metadata finishes the recorded metadata without ticking; uncommitted payload replays the protected operation; changed payload blocks with originals retained. Journal removal is housekeeping after durable completion, not the acknowledgement point. Failures remain explicit and retryable.

Identity move uses the same protocol across source/destination. Persist both raw payloads and metadata transitions first; verify destination success before source removal. Replay recognizes either stage. Cloud record identity stays stable; incomplete moves suppress reconciliation-generated deletion/publication. Annotation-ID collisions require explicit retention and conflict resolution rather than whole-book replacement. Temporary duplicates are preferable to irreversible deletion; do not perform an unjournaled best-effort rollback over concurrent work.

Restore suspends new affected commands/publication, drains active commits, settles or durably retains session work, then applies participants through owners. Incoming operations remain durable and deferred. Persist unfinished restore state; launch must reestablish the barrier before ordinary sync. Reload projections without flushing stale snapshots onto restored data, invalidate stale undo, then resume deliberate reconciliation. Cancellation before durable intent can abandon work; cancellation afterward leaves a resumable operation and releases locks. Acquire coordinator before owners; never call a coordinator from a held owner commit. Same-process ownership is the initial supported writer scope; a second process must not mutate these files concurrently until an explicit interprocess lock protocol is validated.

## Account, backup, migration and rollback

Journal records require version and explicit identity/account evidence when available. A wrong-account callback cannot resume another account's operation or publish it into a new account. Account transition preserves pending work and recovery, clears/rebuilds transport references only through an explicit checked operation, and does not discard tombstone history. Retained creative versions, unknown originals and necessary identity evidence are backup participants. Transport cursors/old delivery queues restore as evidence only; archives never automatically replay old cloud or server commands.

Local owner completion records are immutable, ordered by per-book sequence, and retained through empty-book deletion. The sync coordinator consumes both owners' before/after transitions before comparing the final snapshot; erase/recreate sequences cannot disappear merely because the final bytes match. Ink and highlight delivery positions are committed atomically with resolved entries in a local-ledger journal. A local journal created before any verified iCloud binding remains local account-neutral work under ADR 010; received journals always retain their verified account context. Local plans prepared under an existing binding cannot replay under another binding.

Cursor-bearing book history uses schema 2. Schema 1 remains explicitly readable; it is upgraded when owner histories are consumed. An older schema-1 writer must refuse schema 2 and preserve the original; mixed writer rollout still requires the earlier BF-043 protection gate. A tombstoned annotation's unexpected live payload cannot be reinterpreted as a local recreation without an owner transition proving that recreation. Unknown/orphan received plans retain their raw inbox requirement; a local-ledger plan can replay its fixed metadata without an incoming envelope or owner rewrite.

Existing valid legacy bookkeeping can be read explicitly; introducing incompatible bookkeeping/journals requires older binaries to refuse writes or a rollout requiring all writers updated. Unknown journal/state schema blocks mutation, leaving originals exportable. No bulk payload migration is required; first mutations retain originals. Reverting code is not a data rollback: unfinished journals must be replayed by a compatible build or exported/recovered deliberately. Disable unsafe transport while retaining local editing/data where the owner preconditions permit it.

## Guarantee and validation

Initial guarantee is deterministic recovery from process termination between successful atomic file writes, within one writer process. Atomic rename/write alone is not a proven power-loss durability guarantee; filesystem flush/directory persistence and platform differences require separate validation before claiming one. Kit remains Foundation/Crypto based and portable; AppleKit owns CloudKit and app lifecycle. No annotation is sent to a book server.

Required evidence: injected failures at every write/delete/enumeration boundary, restart after payload success/metadata failure, idempotent duplicate delivery, corrupt/future bookkeeping protection, deletion and erased-stroke retention, conflict-copy failure refusing replacement, stale editor/undo/repair schedules, interrupted identity moves/collisions, restore while receive is active, account transition and unknown fields. Use existing portable suites and isolated Apple component destinations. Simulator interaction, real Pencil and signed multi-device cloud acceptance are independent gates; no such success is established by this ADR.

## Revision 2026-10-02: local mutation history retention (OD-034)

**Context.** The IP-6 rerun showed the local mutation journal growing without limit. Each ink record also stored a copy of the whole book's ink, and every save re-read and re-decoded the entire history. A 4.3 MB book reached 163 MB of history after 56 saves, and the measurement did not finish in 28 minutes. Storage and save latency both grew with the number of saves ever made in a book.

**Product decision (owner, 2026-10-02).** Keep each edit's local history only until iCloud sync has consumed it and a complete automatic backup has captured the annotations after it. Older versions are then recovered from backup recovery points, not from the device's journal.

**Decision.**

- New ink records carry only the changed section (before and after), not a whole-book `original`. That section is enough to replay or recognise the edit. Older records that carry `original` remain valid and are still cross-checked. Highlight records are unchanged: their unit is already the book's small highlights file.
- Settling skips re-validation of completed records. The journal still verifies every checksum and chain link when it reads them, and incomplete records are fully validated before replay.
- `LocalAnnotationMutationJournal.compact(bookID:through:)` removes completed records up to a target. It first writes `base.json`, which names the last compacted record by sequence, operation ID and digest. It then removes completion markers before records, so an interruption leaves only leftovers at or below the base, which readers ignore and the next compaction removes. The chain continues from the base. The head may name the base, and a base that disagrees with a retained record blocks reading. Incomplete records are never compacted.
- `LocalMutationRetention` (Kit) sets the target per book and owner as the minimum of: completed history; sync's consumed sequence when the sync switch is on in a build that can sync (unreadable sync history keeps everything); and the watermarks of the last complete automatic backup when backup is on. Watermarks are read before capture and recorded only after a complete generation is stored. A consumer that is switched off does not hold history.
- The sync engine treats a cursor behind the durable base as deliberate: it moves the cursor to the base and relies on its existing snapshot comparison. That comparison records net additions, edits, erased strokes and deletions. Intermediate states that were never consumed are not replayed. They were never delivered, so no other device can depend on them. A cursor *ahead* of retained history is still refused as lost history.
- Each operation still reads and verifies the journal from disk once. Within one synchronous owner operation, the verified history is reused until the journal itself writes. Across operations, a record file whose file number, size and modification time are unchanged reuses its verified decode. File-type checks use `lstat`. These are performance measures that keep checksum and chain verification; see the measurement evidence.
- AppleKit runs compaction at launch, at foreground, after each backup opportunity and 30 s after annotation changes. It never runs while a restore is pending.

**Alternatives considered.** Keep everything (rejected: unbounded storage and latency). Keep a fixed recent window on the device as well (rejected by the owner for now; it can be added on top of the same base marker). Compact only on sync consumption (rejected: the owner chose to also wait for backup).

**Failure cases.** If backup or sync fails for a long time while switched on, history grows until it succeeds. It now grows by about section size per save rather than book size. Retention metadata that cannot be read keeps everything. A corrupt retention file only delays compaction; it is rewritten after the next complete backup. A crash during compaction leaves ignorable leftovers.

**Rollback.** Builds before this revision do not understand `base.json` and refuse the journal as unrecognized evidence, so they pause editing and sync for that book rather than guessing. Returning to such a build after compaction therefore needs this build or later. No data is lost: payloads, sync state and backups are intact.

**Validation.** `LocalMutationRetentionTests`: section-level records, compaction and continuation, interrupted compaction, tampered base, incomplete records kept, consumer gating, sync reconciliation after a compaction gap including deletions, and highlight compaction. `CloudBackupTests.recordsLocalHistoryWatermarks` covers backup watermarks. Device storage and latency under real Pencil use remain to be measured.
